## Задание

Требуется реализовать thread-safe хеш-таблицу с закрытой адресацией.

Требования к структуре:
- минимально необходимый набор операций: put(key: K, value: V), get(key: K) -> V, size() -> usize, clear(), merge(key: K, value: V, merger: Fn(V, V) -> V) -> V, итератор по парам ключ-значения
- (почти) никогда не блокирующие операции чтения
- однозначный наблюдаемый порядок между завершёнными операциями
За более формальной спецификацией см. Javadoc к ConcurrentHashMap (https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html) в JDK.

## Реализация

В рамках работы реализована потокобезопасная хеш-таблица с **закрытой адресацией** (отдельные цепочки коллизий), с набором операций, близким к используемому в стандартной библиотеке Java для `java.util.concurrent.ConcurrentHashMap` (в качестве ориентира по семантике и составу методов).

### Структура данных и общая идея

Реализовано разбиение таблицы на **сегменты** фиксированного числа (степень двойки, по умолчанию 16). Каждый сегмент — отдельный объект с собственной **таблицей корзин** и блокировкой типа `ReentrantLock`. `ReentrantLock` — взаимная блокировка из `java.util.concurrent.locks`, допускающая повторный захват тем же потоком и обеспечивающая взаимное исключение при доступе к данным сегмента из разных потоков. Ключ по хэш-коду относится к одному сегменту, поэтому операции записи в разных сегментах не мешают друг другу по блокировкам.

Внутри сегмента разработана структура **цепочек**: узлы `HashEntry` содержат ключ, хэш, значение и ссылку на следующий узел. Таблица корзин представлена как `AtomicReferenceArray`, поля связного списка и значения помечены как `volatile`, что используется при организации чтений без блокировки.

### Реализованные операции

- **`get`** — выполняется **без захвата блокировки** сегмента: чтение корзины и обход цепочки; дополнительно используется барьер `VarHandle.loadLoadFence()` для упорядочивания наблюдаемых чтений.
- **`put` / `putIfAbsent`** — выполняются под блокировкой сегмента; при переполнении вызывается **перехэширование** (удвоение числа корзин, переразмещение узлов). Перед увеличением счётчика элементов при вставке нового узла используется `VarHandle.storeStoreFence()`, чтобы наблюдаемость новой записи была согласована с обновлением `count`.
- **`merge`** — также под блокировкой; поддерживается сценарий удаления ключа, если функция слияния возвращает `null` (перестроение корзины без удаляемого ключа).
- **`clear`** — на уровне всей карты последовательно блокируются **все** сегменты, затем для каждого вызывается очистка. Внутри сегмента сначала обнуляется счётчик элементов, затем барьер записи, затем обнуление корзин; так уменьшается риск наблюдаемой несогласованности между «пустым» `get` и ненулевым `size` при конкурентном чтении без блокировки.
- **`size`** — реализовано два уровня: сначала несколько раз суммируются поля `count` по сегментам без блокировок; если сумма «стабилизируется» между проходами, возвращается это значение. Иначе выполняется **полная блокировка всех сегментов** и повторный подсчёт (более дорогой, но согласованный путь).
- **`iterator`** — разработан обход по сегментам и корзинам; возвращаются неизменяемые пары «ключ–значение» для текущего снимка обхода.

Для ключей и значений `null` реализованы проверки с выбросом `NullPointerException` в духе ожидаемого поведения JDK-карты.

### Тесты на гонки (JCStress)

Подключён инструментарий **JCStress**. Реализованы три отдельных сценария:

1. [JCStressTestPutGetVisibility.java](src/test/java/com/example/concurrentmap/JCStressTestPutGetVisibility.java) — после завершения `put` в отдельном потоке два читателя, синхронизированные через `AtomicInteger`, читают одно и то же значение. Проверяется **видимость записи**: недопустимы исходы, когда запись уже завершена, но ни один читатель её не наблюдает.
2. [JCStressTestClearGetRace.java](src/test/java/com/example/concurrentmap/JCStressTestClearGetRace.java) — параллельно выполняются `clear` и поток, который подряд вызывает `get(1)` и `size()`. Задокументирован инвариант **согласованности наблюдений** при единственном ключе в таблице: допускаются согласованное пустое состояние, полное наличие ключа, а также слабый вариант «`size` уже нулевой, а `get` ещё видит старое значение»; **запрещён** исход «ключа нет, но размер сообщает о непустой карте».
3. [JCStressTestMergeConsistency.java](src/test/java/com/example/concurrentmap/JCStressTestMergeConsistency.java) — два потока выполняют `merge` по одному ключу с суммированием; арбитр фиксирует финальное значение. Проверяется, что наблюдаемые промежуточные и финальные значения соответствуют ожидаемому диапазону (корректность слияния при конкуренции).
